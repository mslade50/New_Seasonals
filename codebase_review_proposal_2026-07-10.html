New Seasonals codebase and private-site improvement proposal

The platform has a strong quantitative core and unusually explicit trading invariants. Its main risk is no longer a lack of capability; it is policy duplication across the scanner, backtest engine, reporting jobs, private site, and the separate local execution project. The next phase should consolidate execution semantics, harden the live-order boundary, and turn the private site into a task-oriented operating cockpit.

Scope: Python application and analytics modules, strategy configuration, GitHub Actions, Cloudflare Pages Functions and broker, static private-site source and current built payload, test suite, repository hygiene, and documentation. No production code or configuration was changed.

Executive summary

Strong
Domain modeling

Raw-vs-adjusted basis, risk overlays, tier rules, and point-in-time concerns are documented with rare precision.

Medium
Maintainability

Core behavior works, but several 800–2,200-line functions and synchronized copies make safe changes expensive.

High
Operational drift risk

Live, simulated, reported, and site-described behavior can diverge because policy has multiple sources of truth.

Highest-consequence finding

The Execution page's HTML still says there are “no commands, positions, or click-to-trade yet,” while site/assets/execution.js implements live bracket orders, flattening, cancellation/modification, account selection, and futures workflows. This is a safety defect in the product language. A user must never have to infer whether a surface can place real orders.

The recommended order of work is:

  1. Make the live-order boundary fail closed and make every label match reality.
  2. Resolve the documented OVS Path-2 live/backtest divergence.
  3. Create one pure, shared execution-policy layer and parity tests.
  4. Reorganize the private site around daily decisions and freshness.
  5. Then split monoliths, consolidate duplicate pages/docs, and move large generated data out of Git.

What should be preserved

Explicit market-data basis contract

KEEP

The frozen-dollar-level versus recomputed-relative-level distinction is correct, important, and backed by an ex-dividend regression test. Any refactor should make this contract more enforceable, not abstract it away.

Configuration-driven strategy book

KEEP

strategy_config.py gives the book a recognizable center. Risk multipliers, overlays, universes, and strategy metadata are more auditable than scattered UI constants would be.

Operational provenance

KEEP

The ledger writer provenance, R2 cache distribution, serialized site deploy, idempotency IDs, HMAC relay, and “previous deploy stays up” behavior are thoughtful operational controls.

Graceful degradation with visible state

KEEP

The site payload contract distinguishes failed signal fetches from genuinely empty tabs, and health.json already contains the raw material for a strong freshness experience.

Targeted parity regressions

KEEP

Tests for ex-dividend fills, fragility bands, same-day derating, stop gaps, OLV fill windows, and EOD drawdown rules cover the exact places a trading system tends to drift.

Static-site delivery model

KEEP

The built private site is only about 4.9 MB before the CDN-hosted Plotly library and cleanly separates generated JSON from committed frontend code. A framework rewrite is not necessary to improve it.

Critical recommendations

R01 — Fail closed when Cloudflare Access verification is not configured

P0

Evidence: functions/_access.js returns null and allows the request when ACCESS_TEAM_DOMAIN or ACCESS_AUD is absent. This is explicitly fail-open for endpoints that can relay live orders.

Proposal: for every /exec-* route, missing Access configuration should return 503/401. Add a deployment smoke test that calls the route without a JWT and requires denial. Keep a separately named local-development bypass only in a non-production environment.

R02 — Replace “unknown means assume live” with “unknown blocks mutations”

P0

Evidence: the client deliberately renders unknown mode as live-like but still leaves order controls usable. A stale/missing book should never be enough to permit a mutating request.

Proposal: disable send, cancel, modify, and flatten unless the server supplies a fresh, signed mode and account snapshot. The server—not only the browser—must enforce this freshness. “Unknown” should remain visually alarming but operationally inert.

R03 — Resolve the OVS Path-2 policy divergence before further sizing research

P0

Evidence: project guidance records that live execution retired mild-gap Path 2 while the ledger/backtest still models 407 Path-2 trades and roughly +82R over 24 years. This changes both expected return and capacity.

Proposal: make an explicit product decision: re-enable Path 2 live or set production ledger/report builds to ovs_p1_only. Stamp the chosen policy version into every staged signal, ledger row, report, and site build. Do not leave this as a runtime default hidden in one caller.

R04 — Correct all execution copy and introduce a preview/commit flow

P0

Evidence: site/execution.html describes a heartbeat-only Phase 2a, while the JavaScript implements live order actions. The current final control is a generic browser confirm().

Proposal: label the page “Live Execution Console” when armed. Use a server-validated preview showing account, side, symbol, quantity, entry, stop, target, maximum loss, notional, buying-power effect, order duration, and warnings. Commit the immutable preview token in a second step; require typed symbol confirmation for live entry/flatten operations.

Architecture and correctness

R05 — Build a shared, pure execution-policy package

P1

Evidence: the project repeatedly says “change together” for daily scan, backtest engine, portfolio report, site, and external order staging. OVERFLOW_RISK_OVERRIDES, risk caps, fallbacks, overlay sequencing, and special strategy rules still exist at several call sites.

Proposal: extract deterministic functions for eligibility, signal decision, staged sizing, overlap clamps, daily caps, and exit-policy construction. Inputs should be immutable typed records; outputs should include a policy version and a trace of every multiplier. Keep fill simulation separate because raw/adjusted bar basis differs by use case.

R06 — Centralize market-data access with an explicit price-basis type

P1

Evidence: dozens of direct yf.download calls remain across pages, jobs, and scripts. MultiIndex handling and auto_adjust choices are therefore enforced by convention rather than one adapter.

Proposal: introduce market_data.get_history(..., basis=ADJUSTED_TOTAL_RETURN|RAW_AS_TRADED), normalize MultiIndex output once, return a schema-checked frame, and reject unspecified basis. Add contract tests with multi-ticker, single-ticker, missing-ticker, timezone, dividend, and partial-session fixtures.

R07 — Split the five largest decision functions before adding more strategies

P1

Evidence: AST inspection found backtester.main at 2,196 lines, backtester.run_engine at 1,262, process_signals_fast at 1,015, strat_backtester.main at 923, and run_daily_scan at 873. Several have 200–437 branch nodes.

Proposal: separate orchestration, data preparation, signal evaluation, sizing, fill/exit simulation, portfolio caps, analytics, and rendering. First extract without behavior changes and lock results with golden fixtures. Target functions under roughly 100 lines for policy and under 200 for orchestration.

R08 — Turn freshness metadata into pipeline gates

P1

Evidence: the reviewed build's health.json marked earnings and signals stale, with signals fetched on 28 June while the build was 9 July; meta.json consequently reported signals:false. Several build steps intentionally continue on error.

Proposal: define artifact service-level objectives and severity: block trading/deployment for unsafe stale inputs, deploy with a large degraded banner for noncritical analytics, and allow quiet omission only for genuinely optional research. Publish the same health manifest to email, site, and workflow summaries.

R09 — Replace broad exception swallowing with typed degraded states

P1

Evidence: approximately 279 broad except Exception handlers exist outside scratch/presentation code, and the frontend uses fetchJSONOrNull at 42 call sites. Many are reasonable best-effort boundaries, but they erase the difference between absent, stale, corrupt, unauthorized, and failed.

Proposal: keep best-effort behavior at explicitly named boundaries, but return structured status objects with source, last-good timestamp, error class, and safety impact. Log unexpected exceptions with context and fail closed for signal, sizing, order, and account-state paths.

R10 — Validate strategy configuration against a schema

P2

Evidence: the strategy book is rich but dictionary-based, with many optional keys and fallback defaults distributed across consumers.

Proposal: define dataclasses or a validation model for strategy settings, execution policy, sizing overlays, entry/exit rules, and universes. Validate at import/build time, reject unknown fields, and generate human-readable strategy documentation from the schema.

Private-site UI/UX proposal

The site should be optimized around three time-sensitive user questions: What needs attention now?, What is the current risk?, and What action is safe to take? The current information architecture is a flat list of 12 peers and the landing page begins with a long-horizon portfolio laboratory.

Proposed landing page: Daily Cockpit
Pipeline freshness
prices · earnings · fragility · signals · ledger
Risk posture
fragility · exposure · open risk · overnight stress
Today’s queue
staged · working · filled · missing · exceptions
Execution state
offline / dry-run / live · account · age
Attention feed
failed fetches, stale artifacts, cap trims, overlaps, rejected orders, earnings conflicts
Today’s signals and order chain
decision-ready cards with a clear path to details or safe preview

R11 — Replace the flat nav with task groups

P1

Proposal: group pages as Today (Cockpit, Signals, Orders), Risk & Portfolio (Portfolio, Risk, Charts), Research (Ideas, Seasonal, Options, Entry Lab, Futures Lab), and Operations (Pipeline, Execution). Keep Execution visually isolated and badge it with OFFLINE/DRY-RUN/LIVE.

R12 — Remove stale policy prose and generate it from current config

P1

Evidence: the Portfolio page's fragility panel describes the retired book-wide ramp and says OVS is exempt, while current policy is a FAMILY4 high-fragility throttle. The JavaScript also contains generic midterm and fragility assumptions that no longer represent live policy.

Proposal: distinguish “current production policy” from “research what-if.” Generate the production summary from the same policy manifest used by scan/ledger. Put experimental controls in a clearly watermarked Lab mode that cannot be mistaken for live parity.

R13 — Make data age and source unavoidable

P1

Proposal: add a persistent status rail showing source, “as of,” build time, and freshness for every page. When data is stale, show age and operational consequence (“signals may exist but are not shown”), not merely a missing section. Add a one-click path to Pipeline diagnostics.

R14 — Complete a keyboard and accessibility pass

P1

Evidence: pages lack <main> landmarks and skip links; nav lacks aria-current; sortable headers are mouse-only and lack aria-sort; many labels are not associated with inputs; 11–12px text is common; focus-visible and reduced-motion styles are absent; charts have little textual fallback.

Proposal: meet WCAG AA basics: semantic landmarks, 16px base text, 44px touch targets for operational controls, explicit focus styles, keyboard sort/menu behavior, non-color status labels, chart summaries, reduced motion, and accessible live announcements for order results.

R15 — Lazy-render the portfolio laboratory

P2

Evidence: the Portfolio page loads many payloads and renders a long sequence of Plotly charts/tables in one document. The payload size is acceptable, but eager rendering creates visual and cognitive load.

Proposal: show summary, equity, open risk, and alerts first. Move deep analytics into tabs/accordions and create Plotly instances only when a section becomes visible. Preserve filters in the URL so views can be bookmarked and shared across pages.

R16 — Clarify simulation bases and units

P2

Evidence: the portfolio JavaScript computes on a $750k flat base, displays some curves from $10k, and retains $750k trade-level dollars. This is mathematically defensible but easy to misread.

Proposal: use one visible “Simulation base” control and repeat the basis next to every dollar output. Separate normalized analytics (R, percent, Sharpe) from account-scale dollars. Never mix display bases inside one chart group without an explicit annotation.

R17 — Add browser security headers and reduce HTML injection surface

P1

Evidence: site/_headers currently sets robots, referrer, and cache controls but not CSP, frame protection, MIME sniffing protection, or a permissions policy. Frontend code contains roughly 120 innerHTML assignments and some inline handlers/styles.

Proposal: add Content-Security-Policy, frame-ancestors 'none', X-Content-Type-Options: nosniff, and a restrictive permissions policy. Remove inline handlers and prefer DOM text APIs/templates that escape by construction. If Plotly remains CDN-hosted, pin and integrity-check it or self-host the exact version.

What not to remove

Do not treat the R2 caches, compatibility wrappers, or strategy-specific tests as generic bloat. Several are intentional safety bridges. The deletion criterion should be “no consumer and a proven replacement,” not file age or size alone.

Testing, reproducibility, and engineering quality

R18 — Make the default test command trustworthy

P1

Evidence: repository-wide pytest collection imports scratch/test_agent_option_spread.py, which calls sys.exit at import time and aborts collection. Running only tests/ produced 136 passed, 2 failed, 1 skipped, and 23 warnings.

Proposal: add test configuration with testpaths = tests, prohibit executable work at import time, classify network/integration/research tests with markers, and make one documented command match CI exactly.

R19 — Reconcile the two failing overflow-universe tests with the activation-gate contract

P1

Evidence: tests expect a supplied parquet path to load by default, but load_overflow_universe and load_overflow_meta now default to respect_active=True; with the live gate off they correctly return fallback/empty metadata. The tests do not opt out of the live gate.

Proposal: decide the API contract explicitly. The cleaner test intent is probably respect_active=False for loader unit tests plus separate tests for gate-on and gate-off behavior. Do not weaken the live gate merely to satisfy old expectations.

R20 — Add a dedicated CI quality workflow

P1

Evidence: the workflow set is rich operationally but has no dedicated pull-request test/lint workflow. Site JavaScript passes node --check, but this is not continuously enforced.

Proposal: on every pull request run fast unit/parity tests, Python lint/format checks, JavaScript syntax plus DOM tests, workflow linting, and a no-network site build against fixtures. Add slower ledger parity and security smoke tests on a schedule.

R21 — Lock the runtime and unify workflow installs

P1

Evidence: most dependencies are unpinned, workflows use different install commands, and the ML model requires an exact scikit-learn version. This makes two jobs built from the same commit potentially run different libraries.

Proposal: maintain a human-edited dependency declaration plus a generated lock/constraints file with hashes. Use it in every workflow and local setup. Treat the sklearn model and its feature schema as a versioned artifact; plan a newer-Python/model retraining migration as one controlled project.

R22 — Add golden “one signal, every surface” parity fixtures

P2

Proposal: for each special strategy path, feed the same frozen market/account state into scanner policy, ledger engine, portfolio report, and staging serializer. Assert eligibility, tradeable symbol, risk trace, quantity, entry/stop/target, caps, and policy version. Include dividends, earnings windows, ladder counts, overlap days, high fragility, clustered signals, and missing data.

Sequenced implementation roadmap

Phase 0 · 1–3 days

Make current behavior safe and truthful

  • Fail closed on missing Access config.
  • Block mutations in unknown/stale mode.
  • Correct Execution and fragility copy.
  • Choose OVS Path-2 policy.
  • Fix default test discovery and overflow test contract.
Phase 1 · 1–2 weeks

Install guardrails

  • Add PR CI and locked dependencies.
  • Add security headers and execution smoke tests.
  • Promote health.json into site/workflow gates.
  • Add a Daily Cockpit and grouped navigation.
  • Add policy-version stamps and parity fixtures.
Phase 2 · 3–6 weeks

Reduce structural drift

  • Extract shared execution-policy functions.
  • Centralize market-data basis and normalization.
  • Split scanner and backtest monoliths.
  • Consolidate seasonal pages and project guides.
  • Move large generated datasets/artifacts out of Git.

Suggested success measures

  • One policy version produces identical sizing traces across scan, ledger, report, staging, and site.
  • No live-order endpoint is reachable when Access verification or agent mode is unknown.
  • The default test command runs cleanly from a fresh checkout and in CI.
  • The site landing page answers freshness, risk, attention, and execution state without scrolling.
  • No core policy function exceeds 200 lines; no UI page owns execution semantics.
  • Repository clones no longer carry generated rank/presentation history that can be fetched by checksum.
