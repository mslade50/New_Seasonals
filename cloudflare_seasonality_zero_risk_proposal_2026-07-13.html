Implementation proposal · read-only source architecture

Cloudflare Seasonality Lab

Exact plan for recreating the Streamlit User Input seasonality page on the private Cloudflare site while adding no write path, credential path, or code path capable of mutating the production price bucket or production master parquet.

Prepared 2026-07-13 Decision: use 2000-present production history Production source: read-only New storage: isolated bucket Proposal only — no implementation authorized
Core decision. Production master_prices.parquet remains the canonical source and is read through a new bucket-scoped read-only credential. A pure local exporter derives compact seasonality payloads. Those payloads are written to a separate seasonals-site-data bucket and served by a separate Worker that has no production binding. The existing master updater, production bucket, production workflows, scanner, ledger, and execution systems are not modified.

1. Decision and risk definition

0

New production write permissions

The new publisher receives an Object Read-only token for the existing production bucket. A programming error that attempts PUT, COPY, or DELETE against production is rejected by Cloudflare IAM.

0

Changes to the master updater

The existing 09:30/21:10 UTC master-price workflow and scripts/update_master_prices.py remain untouched.

0

Interactive Yahoo dependencies

The browser and data Worker never call Yahoo. The feature reads the last published R2 projection and remains available even when Yahoo is unavailable.

1

New isolated data product

A separate bucket holds disposable, reproducible, site-only JSON payloads. It is not a second source of truth.

Precise meaning of “zero risk.” No engineering change can remove the pre-existing operational risk of systems that already update production. This design adds zero new capability to mutate production: every new component is either credential-free, production-read-only, or scoped exclusively to the new site-data bucket. Existing production behavior is unchanged.

Non-negotiable invariants

  1. No new script receives the existing R2_ACCESS_KEY_ID / R2_SECRET_ACCESS_KEY production writer secrets.
  2. No new Worker or Pages Function receives the existing CHARTS / production bucket binding.
  3. No new code uploads, copies, deletes, rewrites, compacts, or renames master_prices.parquet.
  4. No new code imports or calls production update, scan, ledger, Sheets, broker, or order-staging modules.
  5. The frontend has no write endpoint and no yfinance fallback.
  6. A failed export cannot replace the current valid site-data manifest.
  7. No automated object deletion or lifecycle cleanup is introduced in Phase 1.

Why a separate Worker is required

The existing Pages project already has the production bucket bound as CHARTS. Cloudflare bindings are capabilities available to project Functions. Even if a newly added Function intended to use only SEASONAL_DATA, it would still run in a project where CHARTS exists. The safer design is a separate Worker/project with exactly one R2 binding: the new site-data bucket. The existing private site adds static HTML/JS only and calls this isolated API.

5. Data contract and calculations

R2 object layout

seasonality/v1/
  current.json
  snapshots/
    2026-07-10T233000Z/
      manifest.json
      prices/
        c3b5...json.gz
        e9a1...json.gz
        ...

Ticker filenames are stable opaque IDs generated by the exporter. Raw ticker strings never become path segments. The manifest maps canonical tickers such as SPY, ^GSPC, or ES=F to their opaque IDs.

Atomic publication

  1. Download the production master with the read-only source token.
  2. Validate schema, row counts, ticker counts, date monotonicity, duplicate keys, and source freshness.
  3. Build the entire snapshot locally without cloud credentials.
  4. Validate every generated object and the manifest locally.
  5. Upload all ticker objects to a new versioned snapshot prefix in the isolated bucket.
  6. Upload that snapshot’s manifest.
  7. Read back and verify manifest/object counts and checksums.
  8. Only then overwrite the small isolated-bucket pointer current.json.

If any step fails before the pointer switch, the private site keeps using the previous complete snapshot. Partially uploaded data is unreachable and cannot affect production.

Per-ticker payload

{
  "schema_version": 1,
  "ticker": "SPY",
  "basis": "adjusted master_prices",
  "history_start": "2000-01-03",
  "asof": "2026-07-10",
  "atr_method": "simple rolling mean of TR, window=14",
  "rows": [
    ["2000-01-03", 91.367599, null],
    ["2000-01-04", 87.795700, null]
  ]
}

Rows contain [date, adjusted_close, atr14]. ATR is computed in Python with the same definition as pages/user_input.py: true range is max(High, previous Close) - min(Low, previous Close), followed by a simple 14-session rolling mean. This is intentionally not the Wilder ATR used by the existing private-site trade sizer.

Browser-side parity scope

  • Ticker selection from the 1,114-symbol manifest; no arbitrary Yahoo fallback.
  • All Years / Election / Pre-Election / Post-Election / Midterm cycles.
  • Recency half-life control.
  • Time-travel cutoff year.
  • Fast-forward trading-day marker.
  • Cycle, all-years, realized-current-year, model-year, and reference-year paths.
  • ATR and optional percentage views.
  • Weighted median, mean, positive percentage, and forward realized volatility for 5/10/21 sessions.
  • Cycle-year paths since 2000, MAE similarity, and actual analog-date detail table.
  • Visible source date, history range, basis, and observation counts.

7. Implementation runbook

Phase 0

Local implementation only

  1. Add the pure exporter, synthetic fixtures, frontend page, math module, Worker code, and tests.
  2. Use the existing local parquet only as read-only test input.
  3. Run the exporter in --dry-run mode into a new local output directory.
  4. Do not configure cloud credentials and do not deploy.
Gate: No tracked production file changes; no external writes; Python and JavaScript parity suites pass.
Phase 1

Owner creates isolated cloud resources

  1. Create Standard-class R2 bucket seasonals-site-data.
  2. Create an Object Read-only token scoped only to the existing production bucket.
  3. Create an Object Read & Write token scoped only to seasonals-site-data.
  4. Create a dedicated Worker deployment token.
  5. Add the new GitHub secrets using the names in this document.
  6. Do not change or reuse the existing production R2 secrets.
Gate: Human review of Cloudflare token scopes. No write permission exists on the new production-read token.
Phase 2

Publish an isolated preview snapshot

  1. Run the dedicated publisher manually.
  2. The download step receives only the production read-only credential.
  3. The export step receives no credentials.
  4. The upload step receives only the site-data bucket credential.
  5. Verify object count, current pointer, source date, checksums, and API responses.
Gate: Production master ETag is observed unchanged before and after. This is a read-only assertion, not a write test.
Phase 3

Deploy isolated Worker and protect it

  1. Deploy Worker name seasonality-data-api from its own configuration directory.
  2. Bind only SEASONAL_DATA = seasonals-site-data.
  3. Attach a same-site custom route such as /seasonality-data/*, or use a dedicated subdomain if the Pages hostname cannot accept a Worker route.
  4. Extend Cloudflare Access to cover the API route.
  5. If cross-origin, allow only the exact private-site origin and credentials required by Access.
Gate: Worker environment inspection shows no production R2 binding, no production secret, and no non-GET route.
Phase 4

Preview the private-site page

  1. Deploy the additive static page to a Cloudflare Pages preview deployment.
  2. Validate SPY, ^GSPC, an equity, an ETF, a futures-style symbol, and an invalid symbol.
  3. Compare the complete result set with Streamlit for fixed control values.
  4. Verify mobile layout, loading states, stale-data messaging, and Access behavior.
Gate: Numeric parity within agreed tolerances and no requests to Yahoo, production R2, execution APIs, or Sheets.
Phase 5

Production display enablement

  1. Deploy the static page and navigation entry through the existing Pages deployment.
  2. Keep the new publisher manual for the first three successful runs.
  3. After three clean runs, enable the independent 23:30 UTC weekday schedule.
  4. Retain the Streamlit page during a validation period; do not delete it.
Gate: Three scheduled publications complete without stale/regressed data and without any production workflow change.

Numeric tolerances

  • Dates, sample membership, cycle-year membership, and observation counts: exact.
  • ATR and forward ATR returns: absolute tolerance ≤ 1e-6 before display rounding.

  • Displayed numbers: identical after the existing UI’s rounding rules.

Rollback sequence

  1. Remove or hide the Seasonality Lab navigation entry through a normal Pages rollback/redeploy.
  2. Leave the Streamlit page available as the fallback.
  3. Disable the new publisher schedule without touching the production updater.
  4. Roll the isolated Worker back to its prior deployment or detach its route.
  5. Do not delete any bucket or object as part of emergency rollback; cleanup is a separate approved action.

10. Ongoing operation

The new bucket is not independently maintained as a second price database. It is a reproducible projection:

Existing yfinance update
  → production master_prices.parquet
  → dedicated read-only publisher at 23:30 UTC
  → isolated seasonality snapshot
  → current.json pointer
  → browser analysis
  • Normal cadence: once after the PM canonical master update.
  • AM publication is unnecessary because the tool is based on completed daily bars.
  • If the source has not advanced, the publisher may skip creating an identical snapshot.
  • The page always displays source asof, snapshot build time, basis, and history start.
  • No manual price blending is needed for the agreed 2000-present scope.
  • No automatic retention deletion is included initially. A site-bucket-only lifecycle policy can be proposed later with separate approval.

13. Final acceptance criteria

  1. The private Cloudflare site reproduces the Streamlit User Input analysis for cached post-2000 tickers.
  2. The browser performs no yfinance/Yahoo request.
  3. Every new cloud credential and binding is incapable of writing to production.
  4. The production master updater and all trading pipelines have zero code changes.
  5. The existing Pages project receives only additive static page assets and no new production-capable Function.
  6. Publisher failure leaves the last complete isolated snapshot active.
  7. Python and JavaScript outputs pass parity tests.
  8. The page shows data vintage and degrades locally without affecting any other private-site page.
  9. No production or site-data object is deleted during implementation or rollback.
