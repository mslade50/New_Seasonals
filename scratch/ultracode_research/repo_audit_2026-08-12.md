### [fragility-risk] Any read exception on rd2_fragility.parquet silently triggers a full PIT-history rewrite with the drifted recompute
File: daily_risk_report.py:815

The append-only merge is only reached if pd.read_parquet(frag_cache_path) and the subsequent index normalization succeed. On ANY exception (partially-written file from a crashed prior run, pyarrow/schema incompatibility after a dependency bump, transient Windows file lock from a concurrent reader such as daily_scan/build_risk_json/the Streamlit page), the code prints a warning and falls through with frag_out = frag_smoothed — the full 10-year in-memory recompute — and writes it over the frozen point-in-time history. CLAUDE.md marks this series as 'APPEND-ONLY ... do not revert to full rewrites; recompute vintages drifted up to ~7 pts on the 63d dial', and it is the sole input to frag_risk_bands live sizing, the exposure-leg kill rules, and the dial_filters entry gates. The job still exits 0, the email still sends, and risk_report.yml then commits and force-pushes the rewritten parquet to main, so the drifted vintage propagates to the next morning's daily_scan checkout. The docstring frames this as a bootstrap path for a 'missing/corrupt cache', but the except clause cannot distinguish genuine corruption from a transient error, keeps no backup of the old file, and does not fail loud — the opposite of the treatment given to the simple-dial shadow, where a read exception merely skips that day's write ('WARNING: simple-dial shadow failed — continuing'). A safer contract for a series that sizes live orders is: on unreadable cache, abort the write (skip the day) and surface an error, reserving full rewrites for an explicit --bootstrap flag.

Failure scenario: The 21:15 UTC PM run is killed mid-write (or pyarrow is bumped in requirements.txt), leaving the parquet unreadable. The next run prints 'WARNING: unreadable fragility cache — full rewrite', replaces the entire frozen 2026-07-02+ point-in-time record with a recompute vintage that sits up to ~7 pts different on the 63d dial, commits it to main, and the 4:47 AM daily_scan sizes every banded strategy off the non-PIT vintage — e.g. a PIT 10d-MA of 48 recomputing to 53 flips FAMILY4 + 3x Bear Fade + Monthly Weak Close from 1.0x to 0.25x (or, with P/C fear OFF, to ZEROED), with no failure signal anywhere.

Verifier: Verified in daily_risk_report.py:800-815: frag_out is pre-set to frag_smoothed (the full in-memory recompute), the except clause only prints 'WARNING: unreadable fragility cache — full rewrite', and the write at 817-842 proceeds unconditionally; risk_report.yml then commits and pushes data/rd2_fragility.parquet (fail-loud only on the PUSH, not on the rewrite). The docstring does document 'a missing/corrupt cache falls back to a full bootstrap write' as intended, but the except cannot distinguish corruption from a transient/environmental read failure, keeps no backup, and the job exits 0 — directly against CLAUDE.md's 'APPEND-ONLY ... do not revert to full rewrites; recompute vintages drifted up to ~7 pts'. Reachability is real, not hypothetical: requirements.txt pins neither pandas nor pyarrow, so every GHA run installs latest and a breaking parquet-read change would silently replace the frozen PIT record that sizes frag_risk_bands, the exposure-leg kills, and the dial_filters gates.
